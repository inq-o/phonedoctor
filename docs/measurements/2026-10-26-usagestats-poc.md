# UsageStats 실증 (2026-10-26, 지표 정리 2026-10-27)

증상 감지(ADR-0003 주 경로)의 전제를 재현 앱으로 확인한 기록. plan.md "증상 감지 설계"의 분류 규칙과 실패 조건을 여기서 정한다.

이 문서가 입증하는 것은 **관측 가능성과 규칙 함수의 동작**이지 제품 탐지 정확도가 아니다. 지표마다 분자·분모·관찰 시간을 나눠 적고, 조건부 통계와 전체 성능을 섞지 않는다. 2026-10-27 수정은 **같은 원자료의 재분석**이며 새 기기 시험이 아니다.

## 1. 환경

| 항목 | 값 |
|---|---|
| 기기 | 에뮬레이터 `Pixel_8_API_35` (Android 15, API 35), 스와이프 잠금, 시간대 Asia/Seoul |
| 재현 앱 | `testapps/bgad` — 알람(`setExactAndAllowWhileIdle`)마다 배경에서 광고 화면을 띄움. **표시 시도**는 `BGAD SHOW`, **액티비티 재개 확인**은 `BGAD RESUMED`(AdActivity.onResume) 로그. 이는 액티비티 생명주기 확인이지 화면 관찰이 아니며, 오버레이형은 AdActivity를 안 써서 RESUMED가 애초에 없음 |
| 관찰 앱 | `testapps/usageprobe` — `PACKAGE_USAGE_STATS`로 `queryEvents` 덤프(E1~E3), 15분 주기 WorkManager 작업(E4) |
| 스크립트 | `testapps/poc/` — `e1.sh`·`e2.sh`·`e4.sh` 실행, `match.py`·`rule_v0.py`·`lag.py` 집계 |
| 원자료 | `ml/data/poc/` (레포 제외) |

- `setExactAndAllowWhileIdle`는 호출 빈도 제한·지연이 있는 API다. E1·E4의 광고 간격(E1 약 20초, E4 240초)은 이 제약 안에서 쓴 값이고, **5초 간격 반복이 지속된다는 보장은 아니다**. 반복 광고 부하 시험은 시험 전용 구동을 따로 만들어 실제 표시 간격을 계측해야 한다(미실시).

## 2. E1 — 표시 방식별로 사용 기록에 남는가

각 광고의 표시 시도(SHOW) 시각 ±2초 안에 `ACTIVITY_RESUMED` 사용 기록 이벤트가 있으면 "이벤트 관측"으로 센다.

| 방식 | 화면 | 액티비티 재개 확인 | 이벤트 관측 | 남은 이벤트 |
|---|---|---|---|---|
| ① 다른 앱 위 표시 권한으로 `startActivity` | 켜짐 | 10/10 | 10/10 | `ACTIVITY_RESUMED` (18~25ms 뒤) |
| ① | 꺼짐 | 5/5 | 5/5 | `ACTIVITY_PAUSED`, `ACTIVITY_RESUMED` |
| ② 전체 화면 알림 (`setFullScreenIntent`) | 켜짐 | 0/10 | — | 헤드업 알림으로 뜨고 액티비티가 안 올라옴. `NOTIFICATION_INTERRUPTION`·`NOTIFICATION_SEEN`만 |
| ② | 꺼짐 | 5/5 | 5/5 | `ACTIVITY_RESUMED` (약 270ms 뒤) |
| ③ 오버레이 창 (`TYPE_APPLICATION_OVERLAY`) | 켜짐 | — | — | 창이라 AdActivity를 안 씀(재개 확인 해당 없음), 액티비티 이벤트도 없음 |

- 액티비티형은 재개 확인된 광고가 모두 이벤트로 관측됨. 오버레이형은 **AdActivity 자체를 쓰지 않아** RESUMED가 없는 것이지, 창이 화면에 뜨지 않았다는 뜻이 아님 — 실제 창 표시 성공 여부는 별도 관찰 대상. 둘 다 사용 기록으로는 귀속 불가 → FR-011 사전 경고로만 보조(ADR-0003 전제와 같음)
- 전체 화면 알림이 화면 켜짐에서 헤드업으로 바뀌는 것은 광고 화면이 아니라 알림이라 US10·알림 쪽 문제
- 시험한 액티비티형 재현 경로·이 OS에서 확인한 것. 다른 구현·OS는 범위 밖

## 3. E2·E3 — 정상 전환과 광고를 가르는 규칙 v0

E2에서 정상 전환 8종을 10번씩 만들고(142개 `ACTIVITY_RESUMED`), E3에서 규칙을 적용함.

규칙 v0 (`testapps/poc/rule_v0.py`). 아래를 모두 만족하는 `ACTIVITY_RESUMED`만 광고로 셈.

| 코드 | 조건 |
|---|---|
| R1 | 시스템 앱이 아님 (`FLAG_SYSTEM`·`FLAG_UPDATED_SYSTEM_APP`). 설치된 앱 전체에서 판정하고, 목록에 없는 패키지는 사용자 앱으로 봄 (아이콘을 숨긴 앱도 셈) |
| R2 | 같은 앱 안 전환이 아님. 직전 `ACTIVITY_RESUMED`가 같은 앱이고, 그 뒤 화면이 꺼진 적 없고, 그 앱의 직전 `ACTIVITY_PAUSED`에서 2초 안이면 같은 앱 안 전환 |
| R3 | 직전 3초 안에 그 앱의 `USER_INTERACTION`(알림 탭 등)이 없음 |
| R4 | 화면 켜짐·잠금 해제 3초 안에, 화면이 꺼지기 전 보던 화면(같은 앱·같은 액티비티)으로 돌아온 게 아님 |
| R5 | 런처 아이콘이 여는 액티비티가 아님 (별칭이면 `ActivityInfo.targetActivity`로 풀어서 비교, 아이콘이 여러 개면 그중 하나) |

### 3-1. 광고 지표 (화면 켜짐 ① 기준)

| 지표 | 값 | 분모·의미 |
|---|---|---|
| 표시 시도(SHOW) | 10 | 재현기가 광고를 띄우려 한 횟수 |
| 액티비티 재개 확인(RESUMED) | 10 | AdActivity가 재개된 광고 건 (광고 건 단위 분모) |
| 이벤트 관측률 | 10/10 | 재개 확인된 광고 중 사용 기록 이벤트가 남은 비율 |
| 조건부 분류율 | 10/10 | 이벤트가 관측된 광고 중 규칙이 광고로 센 비율 |
| 광고 건 단위 탐지율 | 10/10 | 재개 확인 전체 중 규칙이 잡은 비율 |

- 화면 꺼짐 ①·② 각 5/5도 같음(광고 20/20). 광고 1건에 `ACTIVITY_RESUMED`가 여러 개 남아도 1건으로 집계
- **앱 단위 재현율(G2)·대표 실제 앱 탐지율은 미평가.** 위 수치는 재현 앱 1종을 반복한 결과이고, 규칙을 같은 실험을 보며 만들었으므로 규칙 개발 자료와 독립 평가 자료가 분리돼 있지 않음
- SHOW는 표시 시도 로그이지 실제 노출 정답이 아님. 재개 확인(RESUMED)이 없는 광고는 분모에서 뺌

### 3-2. 정상 전환 오탐

| 시나리오 | 정상 전환 | 광고로 셈 (R1 켬) | 광고로 셈 (R1 끔) |
|---|---|---|---|
| 런처 아이콘 탭 | 11 | 0 | 4 (메시지 앱 첫 로그인 중간 화면) |
| 알림 탭 | 10 | 0 | 0 |
| 최근 앱에서 전환 | 10 | 0 | 0 |
| 앱에서 다른 앱 열기 | 20 | 0 | 0 |
| 화면 켜기 | 10 | 0 | 0 |
| 타이머 울림 (화면 꺼짐) | 30 | 0 | 20 (시계 10, 런처 10) |
| 전화 수신 (화면 꺼짐) | 31 | 0 | 30 (전화 10, 런처 20) |
| 앱 안 전면 광고 | 20 | 0 | 0 |
| **합계** | **142** | **0 (0%)** | **54 (38%)** |

- R1을 끄면 오탐이 거의 시스템 앱(런처·시계·전화)에서 나옴. **정상 표본 대부분이 시스템 앱이라 R1이 오탐을 가린 셈** → 사용자 설치 앱(카카오톡 등) 간 링크·복귀·로그인/결제 복귀는 이 표본에 없음. T074에서 따로 재야 함
- 합성 반례로 확인한 규칙 한계(`rule_v0.py` `_check`): 브라우저에서 다른 사용자 앱으로 이동, 이전 앱으로 복귀는 현재 규칙이 광고로 셀 수 있음. 실제 기기의 발생 빈도는 미확인
- R2·R4는 마지막 화면 꺼짐 시각과 직전 화면을 알아야 함 → 주기 작업 사이에 규칙 상태를 저장해야 함

## 4. E4 — 주기 작업이 광고를 얼마나 늦게 보는가

조건 하나를 걸고 40분 동안 광고 ①을 4분마다 10번 띄움. 재개 확인된 광고마다 주기 작업(15분)이 처음 본 지연을 `lag.py`로 분류한다. **조회 여부와 30분 기한(NFR-02 ≤30분) 준수를 별도 축으로 센다** — 31분 뒤 조회는 조회 성공이면서 기한 실패다. `obs_end`(기한 판정 기준)는 작업 실행 시각이 아니라 **실제 실험 종료 시각**(`meta.txt`의 `end`)을 쓴다.

기한 상태: 준수(조회 & ≤30분) · 늦게 조회(조회 & >30분) · 30분내 미조회(미조회 & 30분 관찰함) · 미결(미조회 & 30분 전 관찰 종료).

| 조건 | 설정 | 조회됨 / 미조회 | 기한 준수 / 위반 / 미결 | 조회된 표본 지연 p50 / p95 |
|---|---|---|---|---|
| 평소 | 화면 켜짐·충전 중 | 7 / 3 | 7 / 0 / 3 | 7.1 / 12.0분 |
| 화면 꺼짐 | 충전 중 | 9 / 1 | 9 / 0 / 1 | 8.3 / 16.3분 |
| Doze | 충전 해제 + `deviceidle force-idle` | 3 / 7 | 3 / 0 / 7 | 7.0 / 11.0분 |
| 대기 버킷 rare | `am set-standby-bucket rare` | 10 / 0 | 8 / **2** / 0 | 16.5 / 36.5분 (아래 주의) |
| 강제 종료 | `am force-stop` | 0 / 10 | 0 / 2 / 8 | — |
| 권한 끔 | 사용 기록 접근 거부 | 0 / 10 | 0 / 2 / 8 | — |

- **p50·p95는 조회된 표본만의 조건부 통계다.** 미결 표본을 포함한 전체 지연 분포가 아니고, 이 자료로 NFR-02 충족 여부를 판정할 수 없음(미확인)
- 평소·화면 꺼짐·Doze의 미결 표본은 측정 창(40분)이 끝나 30분 관찰이 못 찬 것. 다음 실행에서 읽혔을지는 관측하지 않음 → 미결로 남김
- **rare "조회됨 10"은 rare 유지 구간의 성과가 아니고, 기한도 2건 위반이다.** rare 구간 40분 동안은 초기 실행과 복원 직후를 빼면 추가 실행이 없었고(runs.csv: begin+0.3s와 end+0.07s 2회뿐), 끝에 버킷을 active로 되돌린 직후 실행이 밀린 광고를 한꺼번에 읽었다. 그래서 지연이 0.5~36.5분이고 36.5·32.5분 2건은 30분 기한 위반. rare 유지 구간의 실제 지연은 별도 시험 필요
- Doze: 초기와 약 15.2분에 실행돼 광고 3건을 읽음(runs.csv 2회). "유지 구간 실행 없음"이 아니라 초기 이후 한 번 돌고 후속 긴 공백. 나머지 7건은 관찰 창 종료로 미결
- 강제 종료: WorkManager 작업이 같이 취소됨(logcat 확인). 첫 2건은 30분 넘게 관찰했는데 미조회(기한 위반), 나머지는 관찰 창이 짧아 미결. 앱을 다시 열기 전까지 감지 멈춤
- 권한 끔: `queryEvents`가 `SecurityException`으로 작업 실패(logcat 확인). 집계는 강제 종료와 같은 모양. 권한을 먼저 확인하고 꺼져 있으면 상태 보고(`DeviceStatus.protection.usageAccess=false`)만 해야 함

실증 범위

- 평소·화면 꺼짐은 active 버킷에서 시작. rare·Doze·강제 종료·권한 거부는 따로 걸어 시험함 → **장기 미사용 실기기의 버킷·제조사 제한을 대표하지 않음.** "현실은 항상 더 나쁘다"고 단정할 근거는 없고, 기기·충전·면제 설정에 따라 다름
- 한 번도 열린 적 없는 앱은 이 에뮬레이터에서 대기 버킷 NEVER라 주기 작업 할당량 0이었음(무효 자료 `ml/data/poc/e4_bucket_never/`). 실제 앱도 설정 마법사에서 화면이 한 번은 열려야 함. 측정에서는 시작 시 버킷을 active로 맞춤. 모든 기기·버전에 같다는 보장은 아님

## 6. 한계·미확인

- **대표 실제 앱 탐지율 미평가**: 재현 앱 1종 반복. 규칙 개발과 평가에 같은 자료를 씀. 실제 애드웨어의 트램펄린·여러 단계 전환·오버레이는 확인 안 함
- **정상 전환 표본이 시스템 앱 위주**: 사용자 설치 앱 간 링크·복귀 오탐은 T074에서 독립 자료로 잼
- **지연 전체 분포 미확인**: 조회된 표본의 조건부 통계만 있음. 미결 표본의 최종 조회 시점, NFR-02 충족 여부는 후속 관측 필요
- **장기 미사용·실기기 미측정**: 갤럭시 절전·초절전·Android 최대 절전, 대기 버킷 하강 과정의 실행 간격, 권한 철회 후 복귀 동작
- **이벤트 보관 기간(E5) 미측정**: plan.md "조회"의 지원 최대 지연 미정. "늦어도 나중에 전부 읽는다"는 무손실 전제를 두면 안 됨
- **반복 광고 중 삭제 완주 미시험**: 재현기는 광고를 3초 뒤 자동 종료. 광고가 계속 뜨는 동안 시니어가 삭제까지 완주하는지, 안전 모드 대안(폰주치의도 꺼지므로 앱 안 흐름과 별도 수동 경로)은 별도 시험 필요
- 조건마다 40분 1회씩. Doze·rare의 실제 지연 상한은 재지 않음

## 7. 재계산 방법 (재분석)

```sh
# 광고 지표(표시 시도·재개 확인·관측·분류)와 정상 오탐
python3 testapps/poc/rule_v0.py ml/data/poc/launchers.csv \
  ml/data/poc/e1/saw.truth.log ml/data/poc/e1/saw.events.csv \
  ml/data/poc/e2/windows.csv ml/data/poc/e2/events.csv
# E4 지연 분류 (조회 여부 × 30분 기한). obs_end는 meta.txt의 end
```
