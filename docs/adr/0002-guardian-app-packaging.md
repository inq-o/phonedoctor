# ADR-0002: 보호자 기능을 같은 앱에 둘지, 별도 앱으로 낼지

- **상태**: Accepted — **안 A (한 앱, 첫 실행에서 역할 선택)**, 2026-10-03
- **날짜**: 2026-10-03
- **결정자**: 최인규

## 맥락

- 시니어 기기와 보호자 기기는 하는 일이 완전히 다름 (시니어: 앱 판정·삭제 / 보호자: 알림·응답)
- 스토어 정책상 **시니어 기기 쪽 앱**만 `QUERY_ALL_PACKAGES`·`isMonitoringTool`·`REQUEST_DELETE_PACKAGES` 선언이 필요
- 계획서 Key Result: "Android 앱 — 시니어 단말용 + 보호자용"

## 선택지

### 안 A: 한 앱, 첫 실행에서 역할 선택

| 항목 | 평가 |
|---|---|
| 사례 | Life360 (가족 전원 같은 앱) |
| 스토어 | 등록 1개, 심사 1회, 테스터 12명 1세트 |
| 정책 | 보호자 기기에도 민감 권한이 선언된 앱이 깔림 → 심사 설명이 복잡, 보호자 폰에서도 "다른 앱 목록 조회" 권한 고지 필요 |
| 사용자 | "어느 앱을 깔아요?" 질문이 없음 |

### 안 B: 별도 앱 2개 (폰주치의 / 폰주치의 가족)

| 항목 | 평가 |
|---|---|
| 사례 | Google Family Link (부모용·자녀용 분리), Qustodio (Kids 앱 분리) |
| 스토어 | 등록 2개, **Play 신규 개인 계정은 앱마다 비공개 테스트 12명·14일 연속**(Play Console 도움말 14151465 확인, 2026-10-03). 같은 테스터가 두 앱에 동시 참여하는 걸 막는 조항은 없음 → 모집은 1세트로 가능, 앱마다 따로 옵트인 필요 |
| 정책 | 보호자 앱은 민감 권한 없음 → 심사 단순. 민감 권한은 시니어 앱에만 |
| 코드 | 멀티모듈이라 `app-senior`, `app-guardian` 두 application 모듈이 core·feature 모듈 공유 (NiA의 `app` + `app-nia-catalog` 구조와 같은 방식) |

### 안 C: 보호자는 앱 없이 웹 + 카카오 알림톡

- 보호자 설치 부담 0
- 단점: 알림톡은 사업자 채널 필요, 웹 푸시는 신뢰성 낮음 → 학기 내 부적합

## 트레이드오프

| | A | B | C |
|---|---|---|---|
| 심사·정책 설명 | 복잡 | 단순 | 단순 |
| 스토어 등록 작업 | 1회 | 2회 | 1회 + 웹 |
| 사용자 혼란 | 적음 | "어느 앱?" 안내 필요 | 적음 |
| 구조 | 앱 모듈 1개 + 역할 분기 | 앱 모듈 2개 | 앱 1 + 웹 |

## 결정

**안 A: 한 앱 + 첫 실행 역할 선택.** ux-flows.md(O1 역할 선택) 그대로.

- 후속: Play 권한 선언(`QUERY_ALL_PACKAGES`·`isMonitoringTool`)과 Data safety 설명에 "보호자 역할로 쓰면 이 권한을 쓰지 않음"을 명시, 보호자 역할에서는 앱 목록 조회 코드 경로가 아예 실행되지 않게 분기
- 심사에서 문제가 되면 B로 전환 — 아래 "feature 모듈 분리" 덕에 비용 작음

## 결과

- 어느 안이든 feature 모듈은 `feature:senior-*`, `feature:guardian-*`로 나눠 둠 → 나중에 A↔B 전환 비용이 작음
- [ux-flows.md](../../specs/001-mvp/ux-flows.md)는 안 A 기준(O1 역할 선택)으로 그렸음. B면 O1만 빠짐
